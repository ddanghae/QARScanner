# QARScanner 전면 신뢰성 감사 수정 PRD

작성일: 2026-08-25
상태: 승인됨 (`prd승인`, 2026-08-25)
대상 저장소: `QARScanner-main-pump-fade-20260824`
대상 기준 커밋: `13142e6 feat: add unified three-mode scan`

## 1. 문제

3개 모드 통합 스캔은 한 번의 실행과 모드별 결과 표시라는 사용자 요구를 충족하지만, 다섯 분야의 읽기 전용 교차 감사에서 다음 신뢰성 문제가 확인됐다.

1. **페이퍼 기록**: LONG 전용 판정식이 SHORT 결과에도 노출돼 정상 봉을 즉시 손실·0R로 오판한다. 기록에 모드와 방향이 없어 같은 심볼의 서로 다른 전략도 구분하지 못한다.
2. **실행 수명주기**: 중단 직후 재시작하면 이전 실행이 새 전역 토큰을 보고 되살아나 진행률·결과를 덮어쓸 수 있다. 대기 중 요청과 재시도도 실제로 취소되지 않는다.
3. **장애 표시**: 종목별 API 오류를 전부 `skipped`로 바꿔 모든 캔들 요청이 실패해도 정상 완료와 후보 0개로 보일 수 있다.
4. **시간 인과성**: 통합 실행에 공통 기준시각이 없고, reversal 피벗은 오른쪽 확인봉이 생기기 전에 구조 이벤트를 과거 시점에 소급할 수 있다. 이미 마감봉만 전달한 뒤 구조 엔진이 최신 봉을 한 번 더 제외하는 경로도 있다.
5. **pump_fade 정렬**: 1h·15m·5m 데이터의 공통 `asOf`가 강제되지 않고, 오래됐거나 중간이 빈 5분봉도 구조 붕괴 근거가 될 수 있다.
6. **계획 불변식**: 음수·0·비유한 가격 또는 방향에 어긋난 손절·목표가 UI와 기록 경계에서 일괄 차단되지 않는다.
7. **표현의 과신**: early의 `급등확률`, `임박` 표현은 34일짜리 단일 검증구간의 구간 적중률을 개별 후보 확률·시간 예측처럼 읽히게 한다. early 청산 연구 문구가 reversal 상세에도 노출된다.
8. **API 보호**: 418도 재시도하고, 429 후 전역 냉각 없이 큐가 계속 진행된다. 응답 weight는 표시만 하고 요청 제어에 쓰지 않는다.
9. **접근성·모바일**: 상세 대화상자의 ARIA와 초점 관리가 불완전하고, 모바일에서는 페이퍼 표가 숨겨진다.

현재 `node tests/run.js`의 162개 테스트는 통과하지만, 실제 `runScan()` 중단 경쟁조건, 전면 API 실패, SHORT 페이퍼, 인과적 피벗 인식 시점을 검증하지 않아 위 결함을 잡지 못한다.

## 2. 회의 결론

reversal/시장구조, early/연구, pump_fade, 실행/API, UI/페이퍼 담당 에이전트 5명이 1차 감사 후 상호 반박 회의를 진행했다. 테스트·보안 담당 1명은 사용량 제한으로 보고를 완료하지 못했다.

합의 사항은 다음과 같다.

- 다음 배포는 오판 차단, 실행 인과성, 장애 정직성, API 보호를 우선한다.
- 점수 가중치, 등급 밴드, 임계값, `early`의 `squeezePct` 상위 50개 절단은 이번에 바꾸지 않는다.
- SHORT 페이퍼는 방향 인식 기록기가 완성되기 전 즉시 차단한다.
- 피벗 수정으로 결과 수가 달라져도 후보를 임의 보충하거나 점수를 재조정하지 않는다.
- `runId`, 취소 신호, API 냉각은 하나의 요청 수명주기로 설계한다.
- 모든 모드는 한 실행에서 고정한 `scanCutoff`를 사용한다.
- 확률·수익성 주장보다 연구 표본의 범위와 한계를 먼저 표시한다.

## 3. 성공 기준

### 실행·장애

1. 중단 후 즉시 재시작해도 이전 실행이 `state`, 결과, 진행률, 완료 이벤트를 변경하지 못한다.
2. fetch, 세마포어 대기, 재시도 backoff가 같은 실행의 `AbortSignal`로 중단된다.
3. 한 모드의 분석 요청이 전부 실패하면 `failed`, 일부만 실패하면 실패 수가 포함된 `degraded`로 표시된다.
4. 실패한 모드가 `후보 없음`으로 표시되지 않고, 통합 실행에서는 정상 모드 결과가 보존된다.
5. HTTP 418은 즉시 실행과 자동 갱신을 중단하고 재시도하지 않는다.
6. HTTP 429는 `Retry-After` 또는 보수적 기본값을 사용해 전역 냉각하며, 4xx 영구 오류는 재시도하지 않는다.

### 시간·신호 인과성

7. 한 번의 통합 스캔에서 모든 모드와 심볼은 시작 시 고정된 `scanCutoff` 이하의 데이터만 사용한다.
8. reversal 구조 이벤트는 해당 피벗의 오른쪽 확인봉이 닫힌 뒤에만 인식 가능하며, prefix 데이터에서도 같은 `signalTime`으로 재현된다.
9. 이미 마감봉 배열을 전달한 경로에서 최신 마감봉을 구조 엔진이 다시 제외하지 않는다.
10. pump_fade의 1h 급등, 15m 신호, 5m 붕괴는 하나의 `asOf`로 정렬되고 미래·오래된·중복·불연속 5분봉은 실패-폐쇄된다.

### 계획·기록·표시

11. 가격 계획은 유한·양수이고 LONG/SHORT별 손절과 TP1·TP2·TP3 순서가 유효할 때만 표시·기록 가능하다.
12. SHORT와 `pump_fade`에는 페이퍼 `기록` 버튼이 비활성화되고 이유가 보인다. 기존 레코드는 삭제하지 않는다.
13. 방향을 알 수 없는 기존 레코드는 성과 분모에서 제외하고 `레거시 방향 미상`으로 격리한다.
14. early 목록은 `급등확률` 대신 `과거 검증구간 적중률`을 사용하고 날짜, 표본 수, 연구표본 기준선, 단일국면 한계를 표시한다.
15. `임박`은 시간 예측이 아닌 `조건 2개 충족`으로 표시한다.
16. reversal 상세에 early 전용 승률·MDD 문구가 나타나지 않는다.
17. 전체 결과에는 세 모드 점수가 서로 비교 가능한 공통 확률이 아니라는 안내가 보인다.
18. 상세 대화상자는 열기·닫기 시 ARIA, 최초 초점, 초점 가두기, 호출 버튼 복귀가 동작하며 모바일에서도 페이퍼 기록을 볼 수 있다.

### 검증

19. 기존 162개 테스트와 신규 결정적 회귀 테스트가 모두 통과한다.
20. 390×844 및 데스크톱 뷰포트에서 전체 스캔, 모드 오류, 무효 계획, 상세 대화상자, 페이퍼 영역을 로컬 headless Chromium으로 확인한다.
21. 변경 전후 reversal 결과 분포 차이를 기록하되 이를 성능 향상으로 해석하지 않는다.

## 5. 제약 조건

- 정적 GitHub Pages와 Vanilla HTML/CSS/JS 구조를 유지한다.
- Binance 공개 REST API만 사용한다.
- 데이터셋 범위나 기준을 속도를 위해 줄이지 않는다.
- 기본은 마감봉이며 실시간 봉 포함 결과는 provisional로 명확히 표시한다.
- 기존 사용자 localStorage 기록을 삭제하지 않는다.
- 실험 점수는 성공 확률이나 기대수익률로 바꾸어 표시하지 않는다.
- correctness 수정과 모델 튜닝을 같은 변경에 섞지 않는다.
- 실제 주문, 계정, 개인 키, 레버리지 확대 권고를 추가하지 않는다.

## 6. 구현 계획

### Builder 1 — 실행/API 수명주기

1. `runContext = { runId, signal, cutoff }`를 생성하고 파이프라인과 API 계층에 전달한다.
2. 전역 재사용 abort token을 제거하고 모든 상태 쓰기 전에 활성 `runId`를 확인한다.
3. 대기 큐와 backoff를 중단 가능하게 만들고 동일 cache key의 in-flight 요청을 병합한다.
4. 요청 결과를 성공, 계산상 제외, 네트워크 실패, rate limit으로 구분해 모드 통계를 만든다.
5. 418/429 정책과 자동 갱신 일시정지를 구현한다.

### Builder 2 — 시간 인과성과 계획

1. 모든 kline을 실행 `cutoff`로 자르고 결과의 `asOf`를 보존한다.
2. pivot에 확인 인덱스·시각을 명시하고 이벤트의 돌파 시각과 인식 시각을 분리한다.
3. 구조 엔진의 마감봉 제외 책임을 한 계층으로 통일한다.
4. pump_fade의 3개 시간봉을 공통 기준시각으로 정렬하고 5분봉 연속성을 검사한다.
5. 공통 계획 validator로 가격 양수·방향·목표 단조성을 검증한다.

### Builder 3 — 페이퍼 안전조치·표현·접근성

1. SHORT/pump_fade 기록을 UI와 함수 경계 양쪽에서 차단한다.
2. 레거시 방향 미상 기록을 삭제 없이 별도 상태로 표시하고 성과 집계에서 제외한다.
3. early 연구 수치의 이름·표본 날짜·표본 수·기준선을 정정한다.
4. 모드별 점수 비비교, provisional, 무효 계획, failed/degraded 안내를 추가한다.
5. dialog 초점/ARIA와 모바일 페이퍼·메뉴 접근성을 수정한다.

### Auditor

3. 취소 후 어떤 비동기 완료도 상태를 변경하지 않는지 확인한다.
4. SHORT 기록 차단이 UI 우회 호출에서도 유지되는지 확인한다.
5. 계획 불변식 실패가 점수 조정이나 후보 보충으로 우회되지 않는지 확인한다.

5. 승인 없이 가중치·임계값·후보 상한을 변경하지 않는다.

## 7. 위험과 완화

1. **reversal 결과 수 변화**: 피벗 인과성 수정은 모든 BOS/CHoCH 결과를 바꿀 수 있다. 변경 전후 고정 fixture와 분포를 비교하고, 후보 부족을 이유로 점수를 보정하지 않는다.
2. **API 요청 증가**: 시간 정렬과 검증이 추가 요청을 만들 수 있다. `endTime`, cache key, in-flight 병합을 사용하고 실제 요청 수를 계측한다.
3. **중단 UX 지연**: 실제 정리가 끝날 때까지 재시작을 잠글 수 있다. 사용자는 `중단 중…` 상태를 보고, 정리 후 버튼이 다시 활성화된다.
4. **레거시 기록 의미 불명**: 기존 스키마에는 방향이 없다. 임의로 LONG으로 추정하지 않고 격리한다.
5. **표현 변경에 따른 수치 감소 인상**: 이는 성능 저하가 아니라 검증 범위를 정확히 표시하는 변경임을 문서에 명시한다.

## 8. 미해결 질문 및 기본 결정안

1. **피벗 교정 포함 여부**: 포함한다. 결과 분포 변화보다 미래참조 제거가 우선이다.
2. **페이퍼 기능 범위**: 이번에는 SHORT/pump_fade 차단과 레거시 격리까지만 한다. 방향·부분익절·장기 pagination을 갖춘 V2는 별도 PRD로 만든다.
3. **early 후보 50개 절단**: 유지한다. 생산 parity와 API 예산 연구 전에는 제거하지 않는다.
4. **접근성 수정**: 안전성 작업과 파일 충돌이 적으므로 이번 범위에 포함하되, 모델 수치 변경과 섞지 않는다.
5. **배포 방식**: 전체 변경을 한 번에 푸시하기 전에 영역별 커밋과 검증 지점을 남긴다.

## 9. 승인 요청

위 기본 결정안대로 구현해도 되는지 승인을 요청한다. 승인 문구는 `진행`이면 충분하다.

전체 페이퍼 기록기 V2까지 이번 작업에 포함하려면 `페이퍼 V2 포함 진행`이라고 승인한다.
